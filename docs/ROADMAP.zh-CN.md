# 路线图

[English](ROADMAP.md)

MQ Studio 正在成为一个覆盖所有消息队列的桌面客户端。每种中间件形态都通过可插拔驱动接入，
驱动声明自己的能力，界面只呈现当前连接的端点真正支持的功能。

本文是交付计划。它所交付的契约在[多 MQ 架构设计](MULTI_MQ_DESIGN.md)，面向用户的简版状态表
在 [README](../README.zh-CN.md)。

## 当前状态

- **已发布** — RocketMQ 4.x / 5.x，通过 Admin API 提供完整功能。
- **已发布** — RabbitMQ 3.x / 4.x，管理面走 HTTP 管理插件，数据面走 AMQP 0-9-1 而不是
  管理接口的 publish 与 get。管理面是完整的：带完整 arguments 的队列、Exchange 与
  Binding、连接与信道、死信、带健康检查与特性开关的节点、虚拟主机、用户与权限、策略与
  参数、定义导入导出、Shovel 与 Federation，以及 stream 队列。
- **已发布** — Kafka 3.x / 4.x，直接走 Kafka 协议本身（franz-go 与 kadm）。带分区、副本与
  配置的 Topic；带每分区 lag 与 Kafka 全部五种 offset 重置的消费组；按 offset、时间戳或
  key 浏览日志并跟随末尾；带 key、header、指定分区与 ack 级别的发送；带生效配置与日志目录
  的 Broker；ACL 与 SCRAM 用户；客户端配额；分区重分配与优先副本选举；以及集群正在跟踪的
  事务。
- **已发布** — MQTT 3.1.1 与 5.0，走 Paho 的两个 Go 库——它们互不重叠：一个只说 3.1.1，
  另一个只说 5.0，而配置成其中一种的 broker 会拒绝另一种的 CONNECT。这是第一个自身没有
  管理面的家族，所以一条连接能做什么是在拨号时按三层决定的：协议本身、多数 broker 会发布
  的 $SYS 树，以及 EMQX 等自带的 REST API。带 QoS、retain 与 5.0 属性的发布；实时订阅
  工作台，会报告丢弃了多少条、会话何时断开；从保留消息得出的主题列表——那是 MQTT 唯一
  能枚举的东西；来自 $SYS 的 broker 计数；以及在管理 API 有应答时，在线客户端与它们的
  会话、订阅、集群节点，并可断开某个会话。探测不到的那一层会连同原因一起上报，而不是
  让页面空着。
- **已发布** — NATS 2.x，走官方 Go 客户端及其 jetstream 子包。这是第二个自身没有管理面
  的家族，也是「可能缺席的东西」最多的一个：连接建立时探测四层——协议、JetStream、服务端的
  HTTP 监控端点、以及系统账户——后三层每一层都有两种不同的缺席原因，指向不同的修复位置，
  所以上报六条退化原因而不是一条。JetStream 的流及其主题、留存策略、存储方式与副本集；
  push 与 pull 两种消费者；按 sequence 浏览与跟随；按 subject 发布，并支持等待回复的
  request；按条数、sequence 或 subject 清理；集群里的服务器与它们的生效配置；客户端连接
  以及断开其中一条；还有账户页，显示各自的 JetStream 用量与被给到的上限。

  核心 NATS 是唯一放不进既有页面的部分，所以它单独占一页。一个 subject 什么都不留：消息
  发给此刻在听的人，之后就没了——没有历史可以往回翻，所以订阅台是实时视图，而不是加了
  过滤条件的消息浏览页。

  有四样东西是明确不做的。没有死信页：消费者用完 max_deliver 之后只是停止重投并发一条
  advisory，消息哪儿也没去。没有位点重置：消费者的起始位置在创建时就定死了，API 不接受
  修改，唯一的「重置」是删掉重建，而那会换掉它的身份。没有未确认投递清单，因为 JetStream
  只报未确认的数量，不报是哪些。账户是只读的：无论配置模式还是 operator 模式，没有任何
  NATS 服务端提供创建账户的请求。
- **已支持** — ActiveMQ Classic 5.x / 6.x 与 ActiveMQ Artemis 2.x，通过 Jolokia 接入，也就是
  两个 broker 都随 Web 控制台附带的那个 JMX-over-HTTP 代理。一个 MQKind 覆盖两种产品，因为对
  使用者来说它们是一个家族；而对驱动来说它们没有一处相同：代理路径不同、MBean 域不同、
  ObjectName 的键不同、属性名不同，连浏览结果的 map 键都毫无交集。到底是哪一个应答，在连接
  建立时就定下来——按哪个 MBean 域响应了 search 来判断。

  这个驱动特别的地方在于：管理面同时就是数据面。浏览和发送在两个产品上都是 JMX 操作，而且
  浏览什么都不会取走——所以消息页不需要 RabbitMQ 那样的 requeue 警告，而且在所有线协议接入点
  都关掉的 broker 上，每个页面照样能用。队列与主题及其堆积、计数器和配置；两种产品上的持久
  订阅，可建可删；带 JMS 消息头、属性和优先级的发送；沿声明反向查出死信目的地，并把消息重投
  回它们当初失败的地方——这是本应用第一个真正能重投的家族；broker 的存储、journal 与生效配置，
  以及它桥接到的其他 broker；还有客户端连接及各自使用的协议。

  AMQP 1.0 是一个可选层，在连接时探测，只为一件 JMX 做不到的事：实时跟随目的地。管理面是
  请求/响应式的，没有推送。只支持主题，这是安全规则——JMS 的消费者会真的消费，挂到队列上会把
  消息取走。接入点关闭的 broker 保留其余全部页面，并说明它处于三种状态中的哪一种。

  有四样东西是明确不做的。没有延迟投递，而两个产品其实都有：调度标注必须是 Long，而两个发送
  操作都只接受 Map<String,String>，所以通过 Jolokia 设的延迟会被接受、被忽略，然后被当成生效了
  报回来。没有位点、没有分区，因为 JMS 两者都没有——消息确认之后就没了，也没有任何东西把目的地
  切成消费者可寻址的分片。没有权限页：两个产品的认证都写在启动时读取的 XML 里，JMX 没有创建
  用户的操作。还有 Classic 的浏览止步于 maxBrowsePageSize，默认 400 条，无论目的地多深；这个
  上限无法通过 JMX 读取，所以页面把它作为一条 caveat 报出来，而不是假装队列就是 400 条深。
- **已交付** — NSQ 1.x，通过 nsqd 与 nsqlookupd 的 HTTP 接口接入。它没有独立的管理协议：
  运维需要问的一切，都是对承载消息的同一批守护进程发起的调用，所以这个驱动完全不需要线协议客户端。
  主题及其堆积量——区分滞留在主题自身队列与滞留在通道里的部分，并对承载它的每个 nsqd 求和；
  通道，也就是这个家族的消费组，带堆积、投递中、延迟待发与重新入队的计数；
  创建、清空、暂停和删除两者，一次覆盖所有守护进程；向指定的某个守护进程发送，可重复发送或延迟投递；
  集群里的 nsqd 与告诉消费者去哪里找它们的 nsqlookupd 并列展示；
  以及已连接的客户端，涵盖 nsqd 上报它们的两种角色——消费者带 ready 计数，指出谁已经不再请求消息；
  生产者带各自已发送的条数。

  有四件事是刻意不做的，而且都源自同一个事实：nsqd 把消息交给消费者之后就不再持有它。
  没有消息浏览，因为堆积数背后没有可回读的日志，也没有任何接口能把消息读回来。
  没有消息 ID，因为它只存在于 nsqd 与当前持有这条消息的消费者之间的连接上。
  没有死信，因为重试超过上限的消息是被丢弃而不是被挪走。
  也没有位点，所以通道的堆积只能被消费或被清空，没有第三种办法。

  有一类客户端是看不到的，而且任何页面都补不上：通过 HTTP 发送的那些。/pub 是一次请求而不是一条连接，
  nsqd 应答完就没有东西可列了——只有通过线协议持有连接的生产者才会出现。

  另外三项缺失关乎 nsqd 上报什么，而不是它存储什么。没有任何速率：它只统计自启动以来的累计条数。
  没有磁盘数据：主题的溢出文件落在 --data-path 指向的位置，而守护进程从不去看它。
  连接表单里也没有凭据，因为它的 HTTP 接口不做任何认证——--auth-http-address 只负责给
  通过 TCP 协议接入的客户端做鉴权，完全不涉及这些端点。

  还有两件事是这个驱动必须做对、而其它家族都测不到的。删除必须同时作用于 nsqlookupd：
  守护进程会忘记被删除的主题，服务发现层不会，所以只删到 nsqd 的操作会把名字留在那里，
  消费者查询时依然能找到它。清空主题时必须一并清空它的通道：nsqd 在消息到达时就把它复制进每个通道，
  所以单独调用 /topic/empty 会返回 200，而页面上的数字纹丝不动。


- **已交付** — Amazon SQS，通过 AWS API 接入。这是第一个没有 Broker 地址的家族：没有任何东西可以拨号，
  所以一个连接就是一个区域加一份凭据，而驱动自己的描述符完全不声明地址字段——这正是阶段 11 铺好的接缝。
  队列会把持有的消息拆成三类展示；标准队列和 FIFO 队列都可以创建、编辑、清空和删除；支持浏览；
  发送支持命名属性、延迟、重复份数，以及 FIFO 队列必需的分组 ID 与去重 ID；
  死信队列通过反向遍历每个队列的重驱策略找出来。

  FIFO 队列这次一并覆盖，没有往后推。.fifo 后缀改变的是顺序、去重和发送时必须携带的字段，
  而列表、创建、清空、删除和读取的方式一点没变——所以差异体现在三个表单字段和两处拒绝上，
  而不是另起一套页面。

  浏览带一条注意事项，而且它是实话。SQS 只有一种读取方式——ReceiveMessage，
  也就是消费者用的那一个：它返回的消息在可见性超时内对其他人不可见，接收次数还会永久加一，
  而重驱策略正是拿这个次数做判断。驱动会立刻把每条消息以 0 秒可见性超时放回去，
  所以窗口大致就是一次请求的时长；但它关不掉这个窗口，也撤不回那个计数。因此是一条明说的注意事项，
  而不是默不作声的尽力而为。

  刻意不做的部分，主要来自一个事实和一条边界。SQS 没有任何形式的订阅——消费者就是调用
  ReceiveMessage 的那个人，服务不记录他是谁——所以没有消费者页、没有 lag、没有位点，
  也没有任何地方能给出消费者数量；队列的订阅者数上报为「未知」而不是 0，因为 0 是服务无法支撑的断言。
  另外服务由 AWS 运行，所以没有集群、没有节点、没有磁盘数据也没有速率：
  SQS 给出的都是单个队列的数字，其余都在 CloudWatch，那是另一套 API、另一份权限。

  还有两处缺失值得点名。没有按消息 ID 查询：ID 在发送时分配、在接收时回带，没有任何索引；
  也没有访问控制页：谁能调用什么由 IAM 决定，那是更外面一层服务，
  只编辑队列策略的页面等于宣称自己在管一份它根本看不到的权限。

- **已交付** — Google Cloud Pub/Sub，通过 Pub/Sub API 接入。这是第二个没有 Broker 地址的家族——
  一个连接就是一个项目加一份 Google 凭据——也是第一个有两类对象的家族。主题会显示有多少订阅在读它，
  可以创建、编辑和删除；订阅是独立的对象，创建、列出、删除都和主题无关；可以浏览订阅、
  带属性和排序键发布消息、创建还原点并做两种回溯；死信主题则通过反向遍历每个订阅的死信策略找出来。

  这两类对象的拆分正是这个阶段存在的理由。Pub/Sub 的主题本身不存消息：一次发布只会送达那一刻
  已存在的订阅，一个都没有就直接丢弃，而服务两种情况都报告成功。所以主题列表以订阅数打头，
  而不是像其他家族那样以深度打头；没有订阅的主题会被告警页面挑出来——这是唯一一种没有其他症状的
  故障，因为被丢弃的消息不会留下任何积压。反过来的情况也有一条自己的规则：删除主题不会删除它的订阅，
  留下来的订阅指向 `_deleted-topic_`，保留着已有内容、继续计费，并且再也收不到任何消息。

  积压量是这个家族唯一给不出的数字，我们把它标为降级并给出原因，而不是编一个出来。
  `num_undelivered_messages` 是 Cloud Monitoring 的指标：它不是管理 API 返回的订阅对象上的字段，
  Pub/Sub 里也没有任何接口会返回它。唯一能造出这个数字的办法是把积压拉下来数一遍，
  而那会把数到的每一条消息都真的投递出去。

  浏览带一条注意事项，理由和 SQS 一样。Pull 是这里唯一的读取方式，也正是消费者用的那个调用：
  读到的内容在被放回去之前对其他读取方不可见，投递次数还会加一——而死信策略正是拿它做判断，
  所以反复浏览能把一条什么都没失败的消息推进死信主题。驱动会把每条消息立刻放回去，
  但没法撤销那次投递计数。

  回溯声明了两种方式，这一点中途做过修正。回到某个时间点和回到某个命名还原点是两种不同的动作、
  有不同的保证；而模拟器只对创建时开启了消息有序的订阅拒绝前者——这是单个订阅的设置，
  与端点本身无关。所以两个能力都保留声明，拒绝则变成调用时的一条错误，并在错误里点名“消息有序”。

  刻意不做的部分，来自服务由 Google 运行这一事实：没有集群、没有节点、没有磁盘数字、也没有速率——
  速率和积压一样属于 Cloud Monitoring。没有访问控制页，因为谁能调用什么由 IAM 决定，那是更外面一层。
  也没有按 ID 查消息：ID 在发布时生成、投递时回带，没有任何东西为它建索引。

- **已交付** — Azure Service Bus，通过 Azure SDK 接入。这是第三个托管家族，也是其中第一个
  需要真正拨号的：区域和项目都不是地址，而命名空间是——这个驱动的两半都要连它，消息走 AMQP，
  拓扑走 HTTPS 上的 Atom。队列和主题在同一个面板，订阅在另一个面板，规则在路由页面，浏览不取走
  任何东西，发送带得动规则要判断的字段，死信则是每个实体自带的那一份。

  消息页面正是这一期被排在这里的原因。peek 的非破坏性是前两个托管家族都做不到的：不加锁、不移动、
  不改投递计数，同时在跑的消费者一条也不会漏。SQS 的读取会把消息藏起来一个可见性超时，Pub/Sub 的
  读取会增加投递次数并因此逼近死信，所以两者都必须给出警告。这一个不需要，而且这个「没有」是在 Go
  和渲染层都被断言的，不靠人去发现——因为它消失的方式是无声的：把 peek 换成 receive，消息照样返回。

  它还能看到消费者根本拿不到的东西。已排程的消息要等到入队时间才放出，已延期的消息被按序号搁置，
  两者都不会交给任何接收方，却都会出现在这个页面上，并标明各自的状态。

  规则是第二个概念，也是路由页面的由来。其他家族的过滤都挂在读取方身上，是一个字段：Pub/Sub 的
  订阅带一个创建时定死的过滤表达式，SQS 的队列则什么都没有。Service Bus 的规则是有名字的对象——
  一个订阅可以挂多条，每条是一个 SQL 或关联过滤器，还可以附一个在消息进入时改写它的动作——所以
  「哪些消息进哪个订阅」是一张拓扑，正好落在此前只有 RabbitMQ 用的那个页面上。交换器就是主题，
  绑定就是规则，绑定的 properties key 就是规则名，而删除正是按名字删。对不上的部分直接拒绝而不是
  近似：主题没有交换器类型，接受一个只会让表单声称建出了一个并不存在的 fanout 主题。

  死信是第三个，它顺带定下了一个能力归属。`CapDLQ` 指的是代理自己命名并填充的、属于每个实体的
  存储；`CapDeadLetterTopology` 指的是被别的对象指向的普通对象，要靠反向遍历配置才能找到。SQS 和
  Pub/Sub 都属于后者。`$DeadLetterQueue` 属于前者：每个队列、每个订阅创建时就自带一个，按实体路径
  加后缀即可访问，且无法被列出、发送、改名或共享。所以只有命名空间为空时，这个页面才可能是空的。

  它刻意没有的东西源自服务由微软运行：没有集群、没有节点、没有磁盘数字、没有速率——速率在 Azure
  Monitor 里。没有任何东西登记为消费者，所以任何地方都没有读取方数量。也没有按消息 ID 查找：消息
  ID 是发送方自己的字段，没有任何索引，真正能定位消息的是浏览据以续读的序号。

  有两件事模拟器无法验证，这里如实记录而不是绕开。它对任何实体都不报告可读的消息数量，所以那里的
  深度和积压全是短横，积压能力也仅针对这一种端点降级——真实命名空间是能回答的。另外，除非目标写成
  绝对 URI，否则它拒绝 `ForwardDeadLetteredMessagesTo`，而真实服务接受实体名。两件事都有对应的
  实时测试，模拟器一旦改变就会变红。

- **已发布** — Amazon Kinesis Data Streams，走 AWS API。第四个托管家族，也是第二个 AWS 家族，
  接入方式和 SQS 一样：一个区域加一次签名请求，表单上任何地方都没有地址。

  它是规范模型第一次被顶回来的家族，原因就是 shard。`Destination` 提供的是 `Partitions`，一个
  整数；而一个流确实被分成 N 个接受写入的分片，所以这个计数是真的，流面板显示的也正是它。但这
  也是一个数字唯一能说出的真话。分片有 id，占据 128 位哈希空间中的一段区间——记录落到哪个分片由
  它决定；分片有自己的读取额度；而且分片是被拆分或与相邻分片合并，而不是被调整大小——旧分片会原
  地留下、关闭，继续保留记录直到过期，并被它的子分片记为父分片。所以细节拿到了自己的端口和页面：
  `CapShards` 背后的 `ShardInspector`，沿用 Redis Stream 的先例——共享词汇没有归处时就新增端口。
  `CapPartitions` 是刻意不声明的：它由 `DestinationStats` 回答，那个页面是「每个分区编号一段读取
  范围」，把分片塞进去会丢掉上面每一个字段。

  估算里有两处判断错了，都和浏览的代价有关。读取不拿走任何东西：`GetRecords` 不移除、不隐藏、
  不标记任何记录，在过期之前任意多个读者都能读到同一条——所以 SQS 和 Pub/Sub 带的那条「浏览会把
  消息从消费者手里拿走」的注意事项在这里根本不成立，一致性测试甚至点名了它们的 key，作为绝不能
  出现在这里的值。真正成立的是另一件事，它有自己的注意事项：一个分片每秒只允许 5 次 `GetRecords`
  和 2 MB，而这份额度由该分片上所有经典消费者共享——所以浏览可能在什么都没拿走的情况下限流一个正在
  运行的应用。驱动把每个分片的调用预算定为 5 次，正是出于这个原因，而不是为了调优。

  消费者页面只有增强扇出这一种。一次注册是一个有名字、有 ARN、可以单独创建和删除的真实对象，也是
  流唯一知道的读者——其他所有读取方都不会注册，位点存在这个连接永远看不到的 DynamoDB 表里。所以
  积压是带原因的降级，而不是被填上一个数字；而且和 Pub/Sub 不同，这个数字在第二个 API 里也不存在。
  读取返回的 `MillisBehindLatest` 是本应用自己的滞后量，它只被用来判断某个分片是否已经读到末尾。

  它刻意不具备的东西，都来自服务由 AWS 运行、以及这里从不把任何东西挪走：没有集群、没有节点、
  没有磁盘数字、没有速率——速率属于 CloudWatch；两种死信页面都没有，因为记录写在哪里就留在哪里，
  直到过期，无论有没有被读过；也没有清空或裁剪，因为只有保留期会移除记录，而它是流上的一个设置。

  有两条别的托管家族都有的告警规则在这里缺席，理由值得和「没有数据可读」分开说：`topicUnsubscribed`
  和 `queueNoConsumer` 在这里几乎会对每一个健康的流报警，因为读取一个流的常规方式根本不注册消费者。

  有一件 LocalStack 无法验证的事，记录下来而不是绕过去。它对每分片读取额度的两半都不做限制——四分
  之一秒内发 20 次调用全部成功——所以注意事项所依赖的机制是通过驱动自身的调用预算来断言的；有一个
  实时测试明确写下了这一点，并会在模拟器哪天开始限制时变红。

- **已完成设计，尚未实现** — 下面列出的两种形态。

## 交付顺序

| 阶段 | 范围 | 完成判据 |
| --- | --- | --- |
| 0–3 | 驱动接缝本身：契约、后端端口、存储与 bridge、前端注册表 | 对 RocketMQ 而言逐屏与之前完全一致 |
| 4 | **RabbitMQ** | 已完成。Exchanges/Bindings 页面存在，且没有 offset 概念泄漏进 UI |
| 5 | **Kafka** | Topic、消费组、lag、浏览与发布端到端可用 |
| 6 | **Redis Stream** | 已完成。Stream、消费组、浏览、发送、待处理列表（PEL）、服务器与其集群、客户端连接和 ACL 用户都读的是真实实例，也没有去假装存在 maxlen 或消息速率。和预期一样是纯增量，新增四个端口：日志的裁剪、订阅的位置、消息的写入，以及待处理列表 |
| 7 | **Pulsar** | 已完成。主题、命名空间与其上的租户、订阅与游标、浏览与跟随、发送控制台、死信与角色授权全部端到端可用；并且没有任何页面去假装这个中间件有 tag、磁盘用量或用户目录 |
| 8 | **MQTT** | 已完成。第一个自身没有管理面的家族：能做什么在连接时按三层探测——协议层、$SYS 树、broker 自带的 REST API——探测不到的那层会说明原因，而不是默默变空 |
| 9 | **NATS** | 已完成。和预期一样是纯增量——没有任何规范页面改变形状——但它是第一个驱动会去读 profile 认证方式（而不只是读凭据）的家族，也正因此暴露了一个拨号时把 RocketMQ 之外所有家族的认证方式重置掉的缺陷 |
| 10 | **ActiveMQ / Artemis** | 已完成。JMS 语义能套进规范页面，除了那些假定存在日志的地方：没有位点、没有分区、没有 trim。换来的是死信页第一次被填满，以及本应用第一个重投操作 |
| 11 | **连接形态** —— 是接缝，不是驱动 | 已完成。一个家族可以声明自己不需要地址，连接表单、profile 存储与探测路径都遵守这一声明；而这件事由驱动自己的 descriptor 说了算 |
| 12 | **NSQ** | 已完成。主题与 channel、没有消息历史因此没有浏览，都已确认。管理面就是这些守护进程自己的 HTTP 接口，所以驱动不需要线协议客户端；真正要做对的是另外三件事：每个数字都是对各自只知道自身状态的守护进程求和、删除必须同时作用于服务发现层、清空主题必须一并清空它的通道 |
| 13 | **Amazon SQS** | 已完成。阶段 11 铺的接缝在这里派上了用场：描述符不声明地址字段，profile 允许 `Endpoints` 为空保存，连接列表在其他家族显示地址的位置显示区域。已确认：没有订阅，因此没有消费者页也没有 lag；没有集群，因为服务由 AWS 运行；只有一种读取方式，而它正是消费者用的那一个——所以浏览带一条注意事项，而不是假装自己无副作用 |
| 14 | **Google Cloud Pub/Sub** | 已完成。订阅确实是独立的对象，而不是读取者的位置——创建、列出、删除都和主题无关，投递配置也全都挂在它身上。但它的 backlog 并不能映射成 lag：`num_undelivered_messages` 是 Cloud Monitoring 的指标，Pub/Sub API 里没有任何接口会返回它，所以这个能力被标为降级并给出原因，而不是填上一个只能靠“把积压拉下来数一遍”造出来的数字 |
| 15 | **Azure Service Bus** | 已完成。peek 不具破坏性，因此这是整个应用里唯一一个完全没有 caveat 的消息页面——而且这个「没有」是被断言的，不靠人去发现。订阅规则确实进了路由页：规则是有名字的对象而不是读取方身上的字段，所以交换器对应主题、绑定对应规则。两件预估没料到的事：死信是代理为每个实体自建的存储，而不是要反向遍历的拓扑；peek 还能看到消费者根本拿不到的已排程和已延期消息 |
| 16 | **Amazon Kinesis** | 已完成。shard 不是分区，而且它拿到的是一个端口和一个页面，而不是几列：分片有名字、占据一段哈希区间，靠拆分与合并而不是调整大小来改变——所以一次扩缩容会留下一个仍然保存着记录的已关闭父分片。两件估算判断错了的事：浏览完全不拿走任何东西，这一点其他托管家族都做不到，它真正消耗的是分片的读取额度，注意事项说的正是这件事；以及积压在任何地方都不存在，连第二个 API 里也没有——经典消费者的位点在 DynamoDB 里，注册的消费者则根本没有位点 |
| 17 | **IBM MQ** | channel 是一等公民，在规范页面里没有对应物，因此单独开一页 |
| 18 | **Solace PubSub+** | Message VPN 是作用域选择器，Pulsar 的命名空间已经验证过这一形态 |

有两个排序决定值得一直放在视野里。

**RabbitMQ 排在 Kafka 前面是刻意的。** Kafka 与 RocketMQ 足够接近，即使抽象是错的它也会顺利
跑通，因此验证不了任何东西。RabbitMQ 在 offset、分区和消费组这三件事上与 RocketMQ 意见相左，
这种不一致才使它成为真正的检验。

**云托管这一档改变的是连接表单，而不只是驱动。** 阶段 12 之前的每一种形态都是「地址 + 可选
凭证」；云托管是「region + 凭证，完全没有地址」—— 这是第一次出现 `Endpoints` 为空却仍然合法
的连接。阶段 11 就是解决它的地方——在第一个托管驱动之前，而不是在它当中：由驱动自己的
descriptor 决定一个家族要不要地址，表单、profile 存储与探测路径都跟随它。

## 各驱动的范围

每个驱动对接什么、点亮哪些规范页面、以及做不到什么。六个规范页面是 `Destinations`、
`Subscriptions`、`Messages`、`Publish`、`Cluster` 与 `Access`。

> RabbitMQ 以下的每一行都是依据各产品公开的管理接口做出的范围估计，属于计划输入而非已验证
> 的行为 —— 每一行都在对应驱动落地时才被确认。

### 自托管

| 驱动 | 管理面 | 点亮的页面 | 主要缺口 |
| --- | --- | --- | --- |
| **RocketMQ** 4.x / 5.x | 基于 remoting 协议的 Admin API | 全部六个 | Proxy 端点能回答的远少于 NameServer，能力在连接时收窄 |
| **RabbitMQ** | HTTP 管理插件，消息面走 AMQP 0-9-1 | 全部六个，外加 Exchanges/Bindings、连接、死信、虚拟主机、策略、定义、数据搬运 | 没有 offset 与分区；没有具名消费组；没有稳定的消息 id；浏览会把读到的消息重新入队，因此带 caveat；Shovel、Federation 与 stream 协议都是插件，未装时能力降级并给出原因 |
| **Kafka** | 基于 Kafka 协议的 AdminClient | 全部六个 | ACL 取决于所配置的 authorizer；浏览是按 offset 区间拉取，不是随机访问 |
| **Pulsar** | Admin REST API + 二进制协议 | 全部六个 | 已完成。tenant 与 namespace 最后两者都做了：既是每个页面上的范围选择器，也有自己的页面 —— 因为主题的地址就是 tenant/namespace/name，选择器的选项总得有个来源 |
| **ActiveMQ / Artemis** | 基于 JMX 的 Jolokia REST，外加用于跟随主题的 AMQP 1.0 | 全部六个，另加死信、连接与主题实时视图 | 已完成。两个产品的管理树没有一个 ObjectName、属性名或消息 map 键是相同的，靠 MBean 域判断哪一个在应答。浏览和发送都是管理操作，因此都不会取走消息、也不需要线协议客户端——可选的 AMQP 层存在的唯一理由是 JMX 无法推送。已确认：没有位点、分区和 trim，因为 JMS 没有；没有延迟投递，因为两个发送操作都只接受 Map<String,String> 而调度标注必须是 Long；没有权限页，因为两者的认证都写在 XML 里；Classic 的浏览止步于 maxBrowsePageSize，该值无法通过 JMX 读取，作为 caveat 报出 |
| **Redis Stream** | `XINFO`、`XRANGE`、`XADD` 等命令 | 全部六个 | 已完成。集群拓扑和 ACL 最后都做了：单机、哨兵与集群三种部署都能读，ACL 用户带键、频道与命令规则 |
| **NATS** | JetStream API、服务端监控端点与 $SYS 账户 | Destinations、Subscriptions、Messages、Publish、Subjects、Cluster、Connections、Accounts、Alerts | 已完成。四层，每一层都在连接时探测：未启用 JetStream 时端点退化为仅发布与订阅；集群相关页面需要监控端点或系统账户其一——监控端点只答一台服务器，$SYS 才答整个集群 |
| **NSQ** | nsqd 与 nsqlookupd HTTP 接口 | Destinations、Subscriptions、Publish、Cluster、Connections、Alerts | 已完成。已确认：没有消息历史，因此没有浏览、也没有消息 ID；没有死信，超过重试上限的消息是被丢弃而不是被挪走；没有位点，堆积只能被消费或被清空；任何地方都没有速率和磁盘数据；也没有凭据，因为 nsqd 的 HTTP 接口不做认证。nsqlookupd 是可选的，profile 没填时该能力会降级并给出原因 |
| **MQTT** | 协议本身没有。连接时探测：$SYS 树，以及 broker 自带的 REST API（如果有）| 概览、主题、订阅、发布、客户端、集群、告警 | 没有消费组、没有 offset、没有历史——消息只在传输途中存在，无人订阅就没了。主题列的是持有保留消息的那些，因为别的都枚举不出来。客户端页需要管理 API，Mosquitto 没有 |

### 云托管

| 驱动 | 管理面 | 点亮的页面 | 主要缺口 |

| **Amazon SQS** | SQS API | Destinations、Messages、Publish、Dead letters、Alerts | 已完成。已确认：没有消费组也没有集群，接收会启动可见性超时因此浏览带 caveat。估算时漏掉了两点：接收还会让消息的接收次数加一，而重驱策略正是拿它做判断，所以反复浏览能把一条什么都没失败的消息推进死信队列；另外死信页其实做得出来——反向遍历每个队列的重驱策略即可 |

| **Amazon Kinesis** | Kinesis API | Overview、Destinations、Shards、Subscriptions、Messages、Publish、Alerts | 已完成。已确认：没有集群，shard 也确实不是分区——但它需要的是一个端口和一个页面，而不是一套列，因为列表必须带上已关闭的分片和它们的血缘。三件估算漏掉的事：浏览不拿走任何东西，所以注意事项改成说分片共享的读取额度；记录没有 id，定位一条记录要靠它的分片加序列号；服务唯一知道的读者是注册的扇出消费者，而它们不带位点——所以积压是降级而不是上报 |

## 由已有驱动覆盖

协议兼容的系统不单独占用一个驱动。它们按自己所讲的协议接入对应驱动，该驱动在连接时把能力
收窄到端点实际支持的范围。

| 按此接入 | 系统 |
| --- | --- |
| Kafka | Redpanda、AutoMQ、WarpStream、Confluent、Amazon MSK、Azure Event Hubs |
| MQTT | EMQX、Mosquitto、HiveMQ、VerneMQ |
| ActiveMQ 或 RabbitMQ | Amazon MQ |
| RocketMQ | 阿里云与腾讯云的 RocketMQ |

## 不在范围内

- **ZeroMQ、nanomsg** —— 没有 broker，也就没有管理面可展示。
- **Celery、Sidekiq、BullMQ** —— 架在 Redis 或 RabbitMQ 之上的应用层任务队列。
  观测它们是另一个产品，而不是再加一个驱动。
